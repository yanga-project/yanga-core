# Generate an SPL Report

The SPL report is one overview site for the whole product line. It links to the reports of the built variants and includes the authored project documentation (README, CHANGELOG). It is generated by a separate, lightweight pipeline: no variant selection, no toolchain, just collect, configure, render.

## Prerequisites

- The variant reports are already built, e.g. `yanga run --variant Disco --platform gtest --target report` for each variant. The collect step picks up whatever it finds; a variant without a built report is simply not listed.
- The project root has the usual `conf.py` and `index.md` used for the variant reports. Both are reused as-is: `conf.py` reads the report configuration from the `REPORT_CONFIGURATION_FILE` environment variable, and `index.md` branches on the report scope.

## Pipeline configuration

Put the four steps in their own pypeline file, for example `spl_pypeline.yaml`:

```yaml
pipeline:
  spl:
    - step: RegisterSplPaths
      module: yanga_core.steps.register_spl_paths
    - step: CollectVariantReports
      module: yanga_core.steps.collect_variant_reports
    - step: GenerateSplReportConfig
      module: yanga_core.steps.generate_spl_report_config
      config:
        project_name: MySPL
    - step: SphinxBuildReport
      module: yanga_core.steps.sphinx_build_report
```

Run it with:

```bash
pypeline run --config-file spl_pypeline.yaml
```

The site is written to `<spl_report_dir>/index.html` (`.yanga/build/spl/reports` by default), with the collected variant reports beside it under `variants/`, mirroring the build tree (e.g. `variants/Disco/gtest/` or `variants/Disco/gtest/Debug/`).

## How the pieces fit

1. `RegisterSplPaths` reads the project settings (`yanga.ini` / `pyproject.toml`) once and registers the resolved `SPLPaths`. All paths — including the report output directory, which honors `create_yanga_build_dir` — come from this single authority; the other steps take no path configuration.
2. `CollectVariantReports` discovers the built reports on disk — each variant build leaves its `report_config.json` marker next to the rendered `reports/` directory — and copies each one into `<spl_report_dir>/variants/…`, registering it in the data registry. That collected layout plus the registrations are the hand-off contract: any source (a local build tree today, a GitHub Release download later) deposits into the same structure, so the following steps never care where a report came from.
3. `GenerateSplReportConfig` turns those registrations into a `report_config.json` with `scope: SPL` — the same `ReportData` payload the variant and component reports use, carrying one HTML link per variant report.
4. `SphinxBuildReport` renders the site with the project's own `conf.py`/`index.md` and fixes the external artifact links. Links to variant reports open in a new tab: each variant report is a separate Sphinx site with its own navigation, so following it in place would leave no way back to the overview.

See [Built-in Pipeline Steps](../reference/steps.md) for the configuration options of each step.
